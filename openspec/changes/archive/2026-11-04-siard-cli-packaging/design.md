# Design

## Context

See proposal.md for motivation. Current state: `siard-cmd` applies the Gradle `application` plugin only — `assembleDist` produces a zip/tar with `bin/siard` scripts and `lib/*.jar`, requiring a pre-installed Java 21. `siard-suite-app` already uses the beryx `runtime` plugin (`runtime`/`runtimeZip`/`jpackage`/`jpackageImage` tasks, per-OS jpackage installer options) — the same machinery is available via the version catalog (`beryx-runtime = 2.0.1`). The app's distribution additionally ships a `siard`/`siard.bat` script generated by a `siardCli` `CreateStartScripts` task wired into `startScripts`/`installDist`. `deliverables.yml` builds the app on a win/mac/linux matrix on `v*` tags and uploads `if-no-files-found: ignore` artifacts — the GUI's `.msi` is produced today, so WiX (and presumably Inno Setup for `.exe`) is already present on `windows-latest`; the `ignore` uploads remain a silent-failure risk worth removing. SFA constraints (correcting the outdated `release-guide.md`): workstations have **no Java installed**, users **cannot download and run** anything — only installers packaged by BIT are deployed — and BIT **forbids JavaFX** in the CLI bundle, so the CLI cannot ride inside the GUI installer.

## Goals / Non-Goals

**Goals:**
- `siard-cmd` produces a jlink application image + zip per OS (win/linux/mac), and jpackage installers: msi + exe (win), deb + rpm (linux), dmg (mac) — all with a bundled runtime containing **no JavaFX**
- The `siard` launcher behaves identically in every artifact (console app, same exit codes)
- Release workflow builds and uploads all CLI artifacts on `v*` tags
- GUI distribution no longer carries a `siard` script

**Non-Goals:**
- Fat/shadow jar (explicitly rejected — serves no audience the installers don't)
- GraalVM native image, package-manager channels (brew/winget/scoop), code signing / macOS notarization (dmg ships unsigned, same as GUI today)
- Changing the existing `siard-cmd` dist zip/tar
- New CLI functionality — artifacts only wrap what `siard-cli` already specifies

## Decisions

### D1 — Reuse beryx `runtime` plugin on `siard-cmd`

Apply `org.beryx.runtime` to `siard-cmd` with a `runtime { ... }` block mirroring `siard-suite-app` minus JavaFX. It provides `runtimeZip` (jlink image zip) and `jpackage` in one plugin, already proven on the GUI. Alternatives: hand-rolled jlink+jpackage invocations (duplicates what the plugin already does), different plugin like `org.beryx.jar`/`badass-jlink` (no benefit over consistency).

### D2 — JDK-only jlink module list

`modules = listOf(...)` contains only JDK modules the CLI needs — derived via `jdeps` during implementation; candidates from the app's list minus GUI needs: `java.sql`, `java.xml`, `java.naming`, `jdk.crypto.ec`, `java.logging`, `java.management`, `java.security.jgss` (plus `java.desktop`/`jdk.unsupported` if jdeps shows Tika/Oracle-driver needs). `additive = true` since the app and all deps are non-modular — they stay on the image classpath. No `javafx.*` module ever appears → satisfies the BIT constraint and the spec. Safe on CI even though the runner JDK is `zulu jdk+fx`: the image contains exactly the listed modules, so the FX-bundled toolchain cannot leak JavaFX into the artifact (verified by the `--list-modules` smoke check).

### D3 — Console launcher with the same JVM args as today

`launcher { noConsole = false }` (console app for stdout/stderr), `jvmArgs` carrying `xercesSaxParserFactory` exactly like the app and the current `applicationDefaultJvmArgs` — otherwise `javax.xml.parsers.SAXParserFactory` resolves via ServiceLoader to the wrong parser (xmlparserv2) inside the bundled runtime.

### D4 — Installer configuration

- **Windows**: both `msi` and `exe`. jpackage accepts one `--type` per invocation and beryx exposes a single `installerType` → `installerType` is set from a project property with a per-OS default, and CI runs `jpackage` twice with `-PinstallerType=<other>` (the app image is reused on the second run). MSI requires **WiX 3.x** and EXE requires **Inno Setup** — both are already on `windows-latest` (the GUI MSI is produced today); verify rather than assume by keeping the upload steps strict. Install **system-wide** (omit `--win-per-user-install`): managed BIT deployments conventionally install machine-wide; the GUI's per-user flag is a GUI choice, not a constraint here.
- **Linux**: `deb` and `rpm` (same two-invocation mechanism; rpm needs `rpmbuild` on the runner → CI `apt install rpm`).
- **macOS**: `dmg` only — pkg adds signing requirements we don't meet; matches the GUI's artifact set.
- Vendor `BAR`, app name `siard-cli`, launcher binary `siard`. Icon: **copy** `archive_red.*` into `siard-cmd` resources — referencing `siard-suite-app` files from the `siard-cmd` build would invert the module dependency direction. Artifact names: `siard-cli-<version>-<os>.<ext>` / image zips `siard-cli-<version>-<os>.zip`.
- **Install location, not PATH**: jpackage console launchers install into the app dir (`/opt/siard-cli/bin`, `siard-cli\` on Windows, inside `siard-cli.app` on macOS) and are not added to PATH — jpackage offers no PATH integration and managed deployments (BIT) should not mutate system PATH anyway. The spec contract is "run `siard` from the installed location"; the user manual documents the install location per OS. PATH symlinks/wrappers are a possible follow-up, not part of this change. On macOS the dmg is a console-app bundle — the image zip remains the ergonomic path for terminal users there.

### D5 — Remove the CLI script from the GUI distribution

Delete the `siardCli` `CreateStartScripts` task and its `dependsOn` wiring in `siard-suite-app/build.gradle.kts`. The `implementation(project(":siard-cmd"))` dependency stays — the app uses `siard-cmd` engine classes (`MetaDataFromDb`, `SiardConnection`, …). Gradle does not validate `mainClass`, so removal is safe but must be verified by inspecting a built app distribution (no `siard*` in `bin/`).

### D6 — CI: extend `deliverables.yml` matrix

Same win/mac/linux job pattern as the app. Tasks are invoked **module-qualified** (`:siard-suite-app:runtimeZip`, `:siard-cmd:jpackage`, …) — the existing step runs unqualified `runtimeZip jpackage`, which would silently fire for both modules once siard-cmd has the plugin; qualify it to keep builds explicit and non-duplicated. Plus the `-PinstallerType=` second invocation on Windows/Linux, `rpm`/`rpmbuild` setup on Ubuntu, and uploads under `siard-cli-*` artifact names. Installer uploads are made **strict** (no `if-no-files-found: ignore`) so a missing artifact fails the release pipeline instead of passing silently — applied to the existing GUI uploads too. Plain dist zip/tar upload stays as-is.

### D7 — Documentation

- `release-guide.md`: correct the SFA constraint paragraph (no Java; no download-and-run; BIT-packaged installer only; no JavaFX in bundle) and replace `java -jar` smoke tests for the CLI with installer/image-zip smoke tests (GUI `java -jar` path stays if still true for the GUI — verify with SFA contact; the GUI constraint may differ).
- `docs/user-manual/*/user-manual.adoc` CLI sections: describe obtaining/installing the standalone CLI (installer or image zip) instead of the GUI-bundled script.
- `README.md`/`justfile`: dev-facing pointers (`./gradlew :siard-cmd:jpackage`) where the CLI script was previously referenced.

## Risks / Trade-offs

- Silent artifact loss via `if-no-files-found: ignore` uploads → make installer uploads strict so a missing artifact fails the release pipeline (WiX/Inno confirmed present — GUI MSI builds today; `rpm` on Ubuntu still needs a setup step)
- jdeps may surface unexpected module needs (`java.desktop` for Tika, `jdk.unsupported`) → smoke-test `archive`/`restore` from a built image on CI or manually before release; missing modules fail fast at launch, not silently
- Unsigned dmg triggers Gatekeeper quarantine → same status as the GUI today; document in release notes, notarization is a follow-up
- Removing the GUI's `siard` script breaks users who relied on it → BREAKING note in release notes; mitigation is the standalone installer
- Two jpackage invocations per OS lengthen release builds → acceptable; artifacts produced in the same job

## Migration Plan

1. Apply beryx plugin + `runtime`/`jpackage` config in `siard-cmd/build.gradle.kts`; derive module list via jdeps
2. Remove `siardCli` task + wiring from `siard-suite-app/build.gradle.kts`
3. Build locally (`runtimeZip`, `jpackageImage`; installers need the matching OS) and smoke-test `siard --version`, `siard archive --help`, module list has no `javafx.*`
4. Extend `deliverables.yml` (tool setup + CLI steps + uploads); verify on a test tag or PR-triggered run
5. Update `release-guide.md`, user-manual CLI sections, README/justfile
6. Release notes: breaking note (CLI no longer in GUI dist), artifact list

Rollback: all changes are build/CI/docs — revert the commit; previous dist zip behavior is untouched.

## Open Questions

- Exact jlink module set — resolved by `jdeps` + image smoke test during implementation (deferrable; doesn't change specs or tasks)
- Whether BIT requires specific MSI properties (upgrade codes, install scope) — resolved by SFA/BIT feedback on the first produced MSI (deferrable)
- Whether the GUI's `java -jar` smoke-test path is still real for SFA — the corrected constraint section will state the installer path for the CLI and flag the GUI line for the same correction if it applies (deferrable to doc update)
