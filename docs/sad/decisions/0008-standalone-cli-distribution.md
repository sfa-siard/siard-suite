# ADR-0008: Standalone CLI Distribution

**Status:** Accepted

## Context

The `siard` CLI previously shipped only inside the SIARD Suite distribution (a `siard`/`siard.bat` start script generated by a `siardCli` `CreateStartScripts` task in `siard-suite-app`) and as a plain Gradle distribution requiring a pre-installed Java 21. This does not serve the two main audiences:

- **SFA staff**: workstations have no Java installed, users cannot download and run binaries — only installers packaged by BIT are deployed. BIT deployment policy also forbids JavaFX in the CLI bundle, so the CLI cannot ride along inside the JavaFX-based SIARD Suite installer.
- **External users**: should not need to install Java before running the CLI.

## Decision

`siard-cmd` is packaged as a standalone product `siard-cli` using the beryx `runtime` plugin (the same plugin already used by `siard-suite-app`):

- **jlink application-image zips** per OS (`siard-cli-<version>-win|linux|mac.zip`) containing a `bin/siard` launcher and an embedded runtime.
- **Native installers** built with jpackage: `msi` + `exe` (Windows, system-wide install — no `--win-per-user-install`), `deb` + `rpm` (Linux), `dmg` (macOS), named `siard-cli-<version>-<os>.<ext>` via a post-`jpackage` rename (jpackage's own naming does not match the release contract).
- The jlink `modules` list is JDK-only, derived via `jdeps` plus dynamically-needed modules (`jdk.crypto.ec`, `java.naming`, `jdk.charsets`) — **no JavaFX modules** in any CLI artifact.
- jpackage is configured with `imageName = "siard"` (names the launcher) and `installerName = "siard-cli"` (names the package). jpackage accepts one `--type` per invocation, so the second installer type is produced with `-PinstallerType=<type>`.
- Launchers are **not added to `PATH`** — jpackage offers no PATH integration and managed (BIT) deployments should not mutate it; the user manual documents the install location per OS.
- The `siardCli` `CreateStartScripts` task and its wiring are removed from `siard-suite-app`; the `implementation(project(":siard-cmd"))` dependency stays (the app uses siard-cmd engine classes).
- The plain `siard-cmd` dist zip/tar (requires Java 21) is kept unchanged.

## Consequences

- Each release publishes `siard-cli-<version>-<os>.zip`, `.msi`, `.exe`, `.deb`, `.rpm`, `.dmg` — all JavaFX-free, all runnable without a pre-installed JRE.
- **BREAKING**: the SIARD Suite application distribution no longer contains a `siard`/`siard.bat` launcher; users who relied on it migrate to the standalone `siard-cli` artifacts.
- `deliverables.yml` builds all CLI artifacts on the win/mac/linux matrix on release tags; installer uploads are strict (`if-no-files-found: error`) so a missing artifact fails the release pipeline.

## Alternatives

- **Fat/shadow jar**: rejected — still requires a pre-installed JRE, serving no audience the installers don't.
- **GraalVM native image**: rejected — build complexity and reflection/resource config risk for a codebase with heavy reflection (JAXB, JDBC drivers).
- **Ship the CLI inside the GUI installer**: rejected — BIT forbids JavaFX in the CLI bundle and the GUI runtime contains JavaFX.
- **Package-manager channels (Homebrew/winget/scoop)**: deferred — possible follow-up, not required for BIT deployment.
